# Теория: почему FMA устроена именно так

Страница объясняет логику FMA: какую проблему она решает, как принципы превращаются в правила, что вы получаете и что теряете, и чем она отличается от Feature-Sliced Design (FSD), DDD и Clean Architecture. Сам skill остаётся коротким; это справочный материал для людей.

## Проблема

Приложения на Angular и NestJS обычно портятся одинаково:

- **Технические папки.** `components/`, `services/`, `models/` растут без границ; одна функция размазана по пяти папкам, и любое изменение задевает все.
- **Скрытая связность.** Любой файл может импортировать любой другой, «приватный» код случайно становится публичным API, появляются циклы.
- **Правила живут в головах.** Ревью один раз ловит нарушение границы, через месяц оно возвращается.
- **Один размер на всех.** Либо каждый CRUD-экран обрастает церемониями (репозитории, мапперы, классы use-case), либо сложные бизнес-правила лежат в сервисе рядом с кодом HTTP и ORM.

FMA — небольшой набор структурных правил против этих четырёх проблем.

## Принципы и их цена

| Принцип | Какую проблему решает | Конкретное правило | Цена |
|---|---|---|---|
| **Сначала домен** | размазанные функции | папки верхнего уровня — домены, а не технические слои | нужно решить, где проходят границы доменов |
| **Фрактальность** | разнобой в структуре; новый подмодуль — новый дизайн | подмодуль устроен так же, как домен | в маленьких подмодулях часть структуры не используется |
| **Слои и матрица зависимостей** | перемешанные обязанности | `ui → state → api → model → repo`, таблица разрешённых импортов | файлов больше, чем при «всё в одном сервисе» |
| **Публичный вход** | скрытая связность | модуль доступен только через `index.ts`; `export *` запрещён | баррели нужно поддерживать |
| **Порты и события между доменами** | домены зависят от внутренностей друг друга | сосед вызывается через порт; асинхронно общаются версионируемыми событиями | косвенность; события добавляют итоговую согласованность |
| **Прогрессивная сложность (ярусы)** | церемонии для простого кода, нет защиты для сложного | по умолчанию `simple`; папка `domain/` переводит модуль в `rich` | два стиля кода в одной кодовой базе |
| **Правила проверяются машиной** | правила живут в головах | `arch:check` роняет сборку при нарушении | настройка инструментов; слои определяются по именам файлов |

## Как это работает

### 1. Домены как модули

Домен — цельная область продукта (`cart`, `orders`, `catalog`). Его код лежит вместе: UI, состояние, API, бизнес-логика, хранение. Цель — **локальность изменений**: типичная правка должна затрагивать один домен. Граница домена — договорённость между людьми и ограничение на этапе компиляции для кода.

### 2. Слои внутри домена

Внутри домена у каждого файла ровно одна роль, а разрешённые направления импортов задаёт матрица (см. [Руководство](/ru/guide) и `SKILL.md`). Важно не число слоёв, а то, что **направление зафиксировано**: `ui` никогда не обращается к `repo`, `model` никогда не импортирует `ui`. С матрицей на вопрос «куда положить этот код?» есть механический ответ.

### 3. Публичный вход

Всё, что домен предлагает соседям, перечислено в одном файле `index.ts` (плюс `exports` модуля NestJS). Это явный контракт: чего нет в экспорте, от того снаружи никто не зависит, а значит, внутренности можно свободно рефакторить. Только именованные экспорты (без `export *`) делают контракт читаемым и проверяемым на ревью.

### 4. Пересечение границ доменов

Три способа, в порядке предпочтения:

1. **Порт у потребителя.** `orders` объявляет, что ему нужно (`CartPort`); реализация — `facade` соседа в монолите или HTTP-клиент между сервисами. Код потребителя не меняется при распиле монолита.
2. **События.** Домен публикует `cart.item-added` (версионируемый контракт в `libs/contracts`), остальные реагируют в своём `model`. Это полностью убирает зависимость на этапе компиляции.
3. **Композиция UI.** Сосед отдаёт готовый компонент через свой `index.ts`; его состояние не импортируется.

Типов портов два из-за одного ограничения: `shared` не импортирует домены. Порт, в сигнатуре которого есть типы домена (репозиторий), принадлежит домену; порт только с общими типами (публикация событий, часы, почта) лежит в `shared`.

### 5. Ярусы

Большая часть кода — CRUD с тонким слоем правил. Для него есть `simple`: `model` обращается к `repo` напрямую. Когда в домене появляются **инварианты между несколькими сущностями** или правила, которые нужно тестировать без БД и HTTP, добавляется папка `domain/`. Это и есть весь переход. Домен становится чистым TypeScript, а `model` обращается к хранилищу только через порт. Публичный вход модуля не меняется, поэтому соседи ничего не замечают.

### 6. Правила проверяют инструменты

Договорённости разрушаются, если при их нарушении ничего не падает. В FMA матрица и правило публичного входа превращены в конфиги для dependency-cruiser, Sheriff и ESLint/oxlint, а `arch:check` запускает их вместе в хуке перед коммитом и в CI. В литературе это называется *architectural fitness function*. Заодно архитектура удобна для AI-агентов: агент читает правила, пишет код, запускает `arch:check` и получает точное имя нарушенного правила.

## Плюсы

- **Локальность изменений** и очевидное место для каждого файла.
- **Границы, которые держатся**, потому что их нарушение роняет сборку, а не зависит от ревью.
- **Дешёвый путь от монолита к сервисам**: порты и контракты событий уже есть.
- **Затраты соразмерны задаче**: простые домены остаются простыми, сложные получают изоляцию и быстрые тесты без БД.
- **Единый словарь для фронтенда и бэкенда**, общие Zod-контракты — единый источник истины для типов и валидации.
- **Предсказуемость для новичков и агентов**: структура одинакова на каждом уровне.

## Минусы и пределы

- **Больше файлов и косвенности**, чем в обычном сервисе; ярус `rich` добавляет порты и маппинг между entity и агрегатом.
- **Баррели чего-то стоят**: у каждого модуля и сегмента `shared` должен быть `index.ts`, а импорты по алиасам должны оставаться неглубокими.
- **Границы определяете вы.** Неверные границы доменов дорого исправлять; FMA не подскажет, где их проводить.
- **Слои определяются по именам файлов** (`*.service.ts`, `*.state.ts`). Файл с другим именем выпадает из правил слоёв.
- **Инструменты непросты**: dependency-cruiser и Sheriff требуют API TypeScript 6 (см. [Проверку правил](/references/enforcement), на английском); часть правил топологии сервисов пока не автоматизирована.
- **Это не полноценный DDD.** Нет event sourcing, карт контекстов и anti-corruption layer как самостоятельных понятий.
- **Итоговая согласованность** появляется, как только вы используете события между доменами; саги и идемпотентные consumer-ы — ваша ответственность.
- **Избыточна для маленьких приложений** без бэкенда или с несколькими экранами.

## Чем отличается от других подходов

### Feature-Sliced Design (FSD)

FSD — методология для фронтенда: горизонтальные слои (`app`, `pages`, `widgets`, `features`, `entities`, `shared`), вертикальные срезы внутри каждого слоя и сегменты (`ui`, `model`, `api`, `lib`) внутри среза. Модуль может импортировать только из нижележащих слоёв, каждый срез отдаёт публичный API.

| | FSD | FMA |
|---|---|---|
| Главная ось | слой по *области переиспользования* (feature, entity, widget...) | *домен*, затем слои внутри него |
| Зависимость между модулями | только вниз, через слои | через порт, событие или компонент-витрину; общей иерархии слоёв нет |
| Область применения | фронтенд | Angular и NestJS в одном монорепо, общие контракты |
| Публичный API | `index` у каждого среза | `index.ts` у модуля и у сегмента `shared` |
| Типичное затруднение | решить, что это: feature, entity или widget | решить, где проходят границы домена |
| Уровни сложности | не предусмотрены | ярусы `simple` / `rich` |

Общее — идея публичного API и проверка правилами линтера. FMA меняет универсальную иерархию слоёв FSD на владение доменом, что лучше подходит бэкендам и большим фронтендам с насыщенной предметной областью.

### Domain-Driven Design (DDD)

В DDD есть *стратегическая* часть (единый язык, ограниченные контексты, карты контекстов) и *тактическая* (entity, value object, агрегаты, доменные события, репозитории).

- **Домен** FMA — облегчённый аналог ограниченного контекста на уровне кода: единица со своей моделью и публичным интерфейсом. Полная карта контекстов не требуется.
- **Ярус `rich` заимствует тактический инструментарий**: чистый `domain/` с агрегатами и value object, порты репозиториев, доменные события.
- **Ярус `simple` делает это сознательно не нужным**: в CRUD-домене агрегаты были бы церемонией.
- FMA добавляет то, что DDD оставляет открытым: конкретную структуру папок, матрицу зависимостей и инструменты проверки.
- В FMA нет event sourcing, обязательного CQRS и формальных паттернов интеграции вроде anti-corruption layer. Их можно добавить, но они вне skill.

### Clean Architecture и Hexagonal (порты и адаптеры)

Clean Architecture раскладывает код по концентрическим кругам (entities, use cases, interface adapters, frameworks) с единым правилом: зависимости направлены внутрь. Hexagonal выражает ту же идею через порты и адаптеры.

| | Clean / Hexagonal | FMA |
|---|---|---|
| Верхнеуровневое деление | обычно по кругам (слоям) | по доменам, затем по слоям |
| Инверсия зависимостей | везде, где граница пересекает круг | только где нужно: в `rich` для хранилища, для междоменных вызовов и инфраструктуры |
| Форма | концентрические круги | линейная цепочка с явной матрицей разрешённых импортов |
| Use case | отдельный класс на каждый сценарий | слой `model` (метод сервиса в NestJS) |
| Фронтенд | не определён | сжатие слоёв под Angular |

FMA сохраняет лучшее из Clean (чистое доменное ядро за портами), но делает его **необязательным и локальным для домена**, а не глобальным правилом, и добавляет вертикальную (доменную) ось, которую Clean оставляет открытой.

### Одной фразой

- **FSD:** слои по области переиспользования, только фронтенд; **FMA:** сначала домены, фронт и бэк.
- **DDD:** метод моделирования; **FMA:** структура кода, в которой можно применить тактику DDD, когда домену это нужно.
- **Clean:** зависимости внутрь везде; **FMA:** инверсия там, где она окупается, плюс упаковка по доменам.

## Когда выбирать FMA

Выбирайте, если у вас монорепо Angular + NestJS, несколько доменов, которые будут расти, и команда (или агенты), которым полезны правила, проверяемые инструментами. Не берите для прототипов, мелких приложений и случаев, когда действительно нужны event sourcing и полный набор DDD.

## Внедрение по шагам

1. Сначала нарисуйте границы доменов на бумаге (существительные бизнеса, а не экраны).
2. Создайте `index.ts` у каждого и переведите импорты на публичные входы.
3. Включите `arch:check` с базовым профилем; сначала исправьте циклы и глубокие импорты.
4. Переводите в `rich` только домены с настоящими инвариантами.
5. Вводите порты и события, когда появляется второй потребитель или распил на сервисы, а не раньше.
